# GRPO Research Summary: RLVR for Structured Extraction with Qwen3-4B QLoRA on a Single RTX 3070 8GB

## 1. Core hyperparameters and recommended ranges

**Learning rate.** TRL's `GRPOConfig` defaults `learning_rate=1e-6` (vs `5e-5` for generic `TrainingArguments`), explicitly because GRPO updates are noisier/higher-variance than SFT cross-entropy ([TRL `grpo_config.py`](https://raw.githubusercontent.com/huggingface/trl/main/trl/trainer/grpo_config.py), lines ~415-419). For LoRA (not full fine-tune), practitioner consensus (Unsloth GRPO notebooks, Phil Schmid's mini-R1 writeup) is to use **5e-6 to 2e-5** for continuing from an SFT adapter — higher than full-FT because only adapter weights update ([philschmid.de/mini-deepseek-r1](https://www.philschmid.de/mini-deepseek-r1)). *Uncertain*: no paper gives a definitive LoRA-GRPO LR sweep for 4B-scale models; treat 1e-5 as a reasonable starting point and tune by watching reward curve smoothness, not loss (GRPO loss is not very interpretable).

**KL / beta.** TRL now defaults `beta=0.0` (no reference model, no KL term) — a deliberate departure from the original DeepSeekMath GRPO paper's `beta=0.04`. The TRL docs justify this citing **Open-Reasoner-Zero** and state it's "common practice to exclude it," referencing **DAPO** and **Dr. GRPO**'s critical analysis (["Understanding R1-Zero-Like Training"](https://huggingface.co/papers/2503.20783)) ([HF GRPOTrainer docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)). For our setting (continuing an SFT adapter with a narrow, deterministic reward), a **small nonzero beta (0.01–0.05)** is safer than the current community default: our policy is close to a well-trained SFT model, we have very limited steps to recover from a bad excursion, and the risk is runaway format drift or degenerate "all-null" collapse rather than needing exploration. Unsloth's guide labels `beta` the "KL coefficient," `0.0` ⇒ faster/less memory ([Unsloth Advanced RL docs](https://unsloth.ai/docs/get-started/reinforcement-learning-rl-guide/advanced-rl-documentation.md)).

**num_generations (group size, G).** TRL default is `8` ([TRL config source](https://raw.githubusercontent.com/huggingface/trl/main/trl/trainer/grpo_config.py) line 64). Given our ~0.96 pilot slot-F1 (many groups near-ceiling → zero-variance groups, see §4), a **larger G (12–16)** increases the chance each group contains at least one partial failure, giving nonzero advantage; but on a single 3070 without vLLM every extra generation is extra wall-clock. A practical compromise for our budget is **G = 8–12**, paired with aggressive prompt difficulty filtering so groups are drawn from prompts likely to produce reward variance (see DAPO's "Dynamic Sampling," §2).

**Temperature / top_p for rollouts.** Unsloth explicitly recommends "a relatively high (1.0) temperature to have diversity in generations which helps learning" ([Unsloth Advanced RL docs](https://unsloth.ai/docs/get-started/reinforcement-learning-rl-guide/advanced-rl-documentation.md)); TRL defaults are `temperature=1.0`, `top_p=1.0`, `top_k=0` (disabled) ([TRL config source](https://raw.githubusercontent.com/huggingface/trl/main/trl/trainer/grpo_config.py) lines 92-97). For structured JSON output, temperature 1.0 risks JSON-validity failures burning rollout budget; a reasonable compromise is **temperature ≈ 0.8–1.0, top_p ≈ 0.95**, relying on the JSON-validity reward term to push the distribution back toward well-formed output rather than clamping sampling diversity away.

**max_completion_length.** TRL default is `512` ([TRL config source](https://raw.githubusercontent.com/huggingface/trl/main/trl/trainer/grpo_config.py) line 70). Given your completions are 200–600 tokens, set `max_completion_length ≈ 640–768` to avoid truncating thinking+JSON, but keep it as tight as plausible since generation cost without vLLM scales roughly linearly with max length and group size.

**epsilon / epsilon_high (Clip-Higher).** TRL default is symmetric `epsilon=0.2` with `epsilon_high` defaulting to the same value if unset ([TRL config source](https://raw.githubusercontent.com/huggingface/trl/main/trl/trainer/grpo_config.py) lines 178-185). DAPO's "Clip-Higher" trick decouples the bounds and recommends **raising only the upper bound (ε_high ≈ 0.28)** to combat entropy collapse — low-probability "exploration" tokens are otherwise unable to gain probability mass fast enough, while high-probability tokens are already easy to reinforce ([DAPO paper, §3.1](https://arxiv.org/html/2503.14476v2)). Unsloth's docs repeat "DAPO recommends 0.28" for `epsilon_high` ([Unsloth Advanced RL docs](https://unsloth.ai/docs/get-started/reinforcement-learning-rl-guide/advanced-rl-documentation.md)). Given our model is already near-ceiling and we want *stability* over *exploration*, keep ε=0.2/ε_high=0.2 initially; only raise ε_high if you observe entropy collapse (near-identical completions within a group).

**num_iterations (μ).** Default `1` (single epoch over collected rollouts before resampling) ([TRL config source](https://raw.githubusercontent.com/huggingface/trl/main/trl/trainer/grpo_config.py) line 176; Unsloth docs confirm default 0/1 behavior). With `μ=1` the clipped objective degenerates to the unclipped surrogate — simpler and safer for a short run; raising μ to 2 reuses rollouts for more gradient steps (cheaper, since generation is your bottleneck) but increases off-policy drift risk within the inner loop. **Given rollouts are expensive on your hardware, μ=2 is worth trying** to amortize generation cost, watching `clip_ratio/*` metrics for blow-up.

**loss_type.** TRL's default changed to **`"dapo"`** (global-batch, active-token normalization) ([TRL config source](https://raw.githubusercontent.com/huggingface/trl/main/trl/trainer/grpo_config.py) line 237; also stated as Unsloth's default). This avoids the length bias the original sample-level GRPO loss has, which DAPO shows under-penalizes long responses, and which Dr. GRPO shows (`"dr_grpo"`, normalize by a constant ≈ `max_completion_length`) still isn't fully removed by DAPO's token-level fix but is simpler ([Dr. GRPO / "Understanding R1-Zero-Like Training"](https://arxiv.org/abs/2503.20783); [HF GRPOTrainer docs, Loss Types](https://huggingface.co/docs/trl/main/en/grpo_trainer)). For thinking-mode Qwen3 where completion length naturally varies a lot across languages (Hebrew/Persian token-per-char ratios differ from English), **either `"dapo"` (current default) or `"dr_grpo"` is appropriate**; avoid plain `"grpo"` and `"bnpo"` is equivalent to `"grpo"` when `per_device_train_batch_size==1`.

**scale_rewards.** Default `"group"` (normalize by within-group std — the original GRPO formula) ([TRL config source](https://raw.githubusercontent.com/huggingface/trl/main/trl/trainer/grpo_config.py) line 227). Dr. GRPO shows std-scaling introduces a **difficulty bias**: easy groups (low reward variance) get amplified advantages, hard/degenerate groups (all-zero) get suppressed ([Dr. GRPO paper](https://arxiv.org/abs/2503.20783)). Given we expect many near-ceiling (low-variance) groups in our ~0.96-F1 regime, `scale_rewards="group"` could inflate noise on exactly the groups least informative. The TRL docs also mention a hybrid from **Lite PPO** ("Part I: Tricks or Traps?"): mean at group level, std at **batch** level (`scale_rewards="batch"`), shown "more robust" ([HF GRPOTrainer docs](https://huggingface.co/docs/trl/main/en/grpo_trainer); [Lite PPO paper](https://huggingface.co/papers/2508.08221)). **Recommendation: try `scale_rewards="batch"` first, with `"none"`/`False` as a fallback** if training is unstable — this is one of the more consequential, under-discussed choices for your near-ceiling setting.

**importance_sampling_level.** TRL default is `"token"`. GSPO (Qwen team) argues **sequence-level** importance ratios (average per-token ratio to one sequence-level number) are more stable, especially for MoE and for rewards that are inherently sequence-level (exactly our case: F1/record-level rewards are computed on the whole JSON, not per-token) ([GSPO paper](https://arxiv.org/abs/2507.18071); Unsloth docs attribute this recommendation explicitly: "GSPO shows sequence-level sampling often gives more stable training for sequence-level rewards" ([Unsloth Advanced RL docs](https://unsloth.ai/docs/get-started/reinforcement-learning-rl-guide/advanced-rl-documentation.md))). **Given our reward is a whole-sequence scorer, `importance_sampling_level="sequence"` is well-motivated** and worth a direct test against `"token"`.

**steps budget.** With ~2-3h budget and slow HF-generate rollouts (no vLLM), expect on the order of **tens to ~100 optimizer steps**, not thousands — this is fundamentally a *few-hundred-sample curriculum* RL run, closer in spirit to "RL as light post-SFT polish" than full R1-Zero-style training.

## 2. Variants & fixes available in TRL today

| Variant | Core idea | In TRL `GRPOConfig`? |
|---|---|---|
| **DAPO** (Clip-Higher, Dynamic Sampling, token-level loss, Overlong Reward Shaping) ([paper](https://arxiv.org/abs/2503.14476)) | Decoupled ε_low/ε_high; filter zero-gradient groups (accuracy∈{0,1}) via oversampling; token-normalized loss; penalize/truncate overlong completions instead of zero-reward | `epsilon_high`, `loss_type="dapo"` ✅. **Dynamic Sampling (filtering accuracy-1/0 groups) is NOT built into TRL's trainer loop** — TRL doesn't do the "oversample until batch filled" mechanic; you'd need a custom dataset sampler/wrapper or pre-filtering (see §4). `mask_truncated_completions` approximates part of "overlong reward shaping" but Unsloth's own docs flag a **bug**: it can zero the entire completion mask and NaN the KL term when many completions are truncated — "we recommend to disable it" ([Unsloth Advanced RL docs](https://unsloth.ai/docs/get-started/reinforcement-learning-rl-guide/advanced-rl-documentation.md), citing [unsloth-zoo source](https://github.com/unslothai/unsloth-zoo/blob/e705f7cb50aa3470a0b6e36052c61b7486a39133/unsloth_zoo/rl_replacements.py#L184)). |
| **Dr. GRPO** ([paper](https://arxiv.org/abs/2503.20783)) | Removes response-length bias by normalizing by a constant instead of sequence length; argues against std-scaling (difficulty bias) | `loss_type="dr_grpo"` ✅, `scale_rewards=False/"none"` ✅ |
| **GSPO** ([paper](https://arxiv.org/abs/2507.18071)) | Sequence-level (not token-level) importance ratios and clipping | `importance_sampling_level="sequence"` ✅ |
| **SAPO** (soft gating, Qwen team, Nov 2025) | Smooth sigmoid trust region instead of hard clip, asymmetric temps for pos/neg advantage | `loss_type="sapo"` ✅ (very new; treat as experimental) ([HF GRPOTrainer docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)) |
| **REINFORCE++ / RLOO** | Simpler leave-one-out baselines, no clipping/groups the same way | Not exposed as `GRPOConfig` options; these are separate TRL trainers (`RLOOTrainer`). *Uncertain* whether worth switching — GRPO's group-normalized advantage is a reasonable RLOO variant already for your deterministic reward. |

Given your single-GPU, short-budget setting, the realistically available, well-supported levers are: `loss_type` (`dapo` default, try `dr_grpo`), `epsilon_high` (Clip-Higher), `scale_rewards` (`group` vs `batch` vs `none`), `importance_sampling_level` (`token` vs `sequence`), and `beta`. True DAPO-style **dynamic sampling** must be implemented by you at the data-loading level (pre-filter or over-sample-and-discard), since TRL's trainer does not natively re-sample until a batch of non-degenerate groups is filled.

## 3. Reward design for extraction / structured-output RLVR

Your reward (slot-F1, record-F1, null accuracy, decoy penalty, hallucination penalty, JSON-validity) is a well-chosen **dense, multi-component reward** rather than a single sparse exact-match signal — appropriate because RLVR with a single 0/1 "exact match" reward is known to starve the gradient when correctness is partial, which is exactly the DAPO "accuracy=1 or 0" degeneracy problem generalized to continuous F1 space ([DAPO §3.2](https://arxiv.org/html/2503.14476v2)). TRL supports this natively via **multiple reward functions + `reward_weights`** (one weight per `reward_funcs` entry; defaults to all-1.0) — exactly the mechanism to combine your components, logged individually as `rewards/{name}/mean` and `rewards/{name}/std` ([HF GRPOTrainer docs, Logged metrics](https://huggingface.co/docs/trl/main/en/grpo_trainer)).

**Format reward weighting.** JSON-validity should be weighted so it dominates early (gate) but doesn't swamp the content signal later — a common anti-pattern noted broadly in RLVR literature (e.g., Tulu 3's RLVR discussion, ["Tulu 3" paper](https://arxiv.org/abs/2411.15124)) is that a model learns to game a cheap/easy-to-satisfy format reward instead of improving content. Since your SFT model already emits valid JSON reliably, JSON-validity reward should act as a **small penalty for rare failures** (low weight, asymmetric: near-zero when satisfied, strong negative when violated) rather than a large positive incentive that competes with F1 terms.

**Reward-hacking risks specific to extraction:**
- **Null-everything hacking**: if "null accuracy" and "hallucination/decoy penalty" are weighted heavily relative to slot-F1 recall, the model can learn to predict `null`/empty for ambiguous or long-range slots to dodge hallucination penalties, trading recall for precision in a way gold evaluation won't reward but your RL reward might. Verify your reward aggregate penalizes under-population (recall) at least as strongly as hallucination (precision) — compute a quick audit of reward-vs-recall correlation on pilot rollouts before the full run.
- **Verbose thinking inflation**: DAPO and Dr. GRPO both document that naive GRPO (length-normalized sample-level loss) rewards length growth, especially for incorrect completions, because longer wrong answers are diluted less per-token ([DAPO](https://arxiv.org/abs/2503.14476), [Dr. GRPO](https://arxiv.org/abs/2503.20783)). Using `loss_type="dapo"` or `"dr_grpo"` (not plain `"grpo"`) mitigates this. Additionally, consider a mild length penalty or length cap matched to completion budget so `<think>` doesn't balloon and eat your rollout-time budget on a slow, non-vLLM setup.
- **Decoy/distractor copying**: if the decoy penalty is too soft relative to slot-F1 reward for *any* match, the model may learn that copying distractor spans sometimes get partial credit via loose partial-span matching — tighten partial-span thresholds or add an explicit decoy-detection sub-reward if this shows up in pilot rollouts.

## 4. Data/curriculum — difficulty filtering for small datasets

Because your SFT model is already ~0.96 slot-F1, a large fraction of your ~500-600 prompts will yield **all-identical (near-ceiling) rewards across the group → zero advantage → zero gradient**, exactly DAPO's "accuracy=1" degeneracy, generalized to F1 ([DAPO §3.2](https://arxiv.org/html/2503.14476v2)). TRL logs this directly as **`frac_reward_zero_std`** — "the fraction of samples in the generation batch with reward std of zero" ([HF GRPOTrainer docs, Logged metrics](https://huggingface.co/docs/trl/main/en/grpo_trainer)) — monitor this as your primary curriculum-health signal.

Recommended pipeline, synthesizing DAPO's **online dynamic sampling** (filter in the loop) and **offline difficulty filtering** used by recipes like **Kimi k1.5**/**Skywork-OR1**/**Polaris** (pre-score each prompt's pass-rate with the base/SFT model before RL, keep only prompts in a "learnable" difficulty band, neither trivial nor impossible) — *note: I could not re-verify exact Skywork-OR1/Polaris hyperparameter tables live (their hosted docs failed to resolve in this session), so cite these as directionally-correct, commonly-referenced practices rather than verbatim quotes*:
1. **Offline pre-filter**: run your current SFT+LoRA checkpoint over all ~500-600 prompts with the real reward scorer, sampling k=4-8 completions per prompt at train-time temperature. Compute per-prompt reward mean/std. **Drop prompts where std≈0 and mean≈max** (already solved) — these cannot produce gradient under GRPO's group-normalized advantage. Keep prompts where std>0 (mixed success) and prompts that are hard-but-not-impossible (some nonzero partial reward); consider dropping prompts where **all** rollouts score ~0 too (DAPO's accuracy∈(0,G) constraint, generalized), since an all-zero group also has zero within-group variance and zero gradient under std-normalization, and — more importantly for a tiny budget — spending expensive non-vLLM rollouts on genuinely unsolvable prompts is wasteful.
2. With only ~500-600 source prompts, after filtering you likely retain a **few hundred "productive" prompts** — this is fine; RL with verifiable rewards is known to work with surprisingly small prompt sets when each prompt is informative (this is the core argument of **Dynamic Sampling**-style approaches and of your task's very premise, "focused on hard cases").
3. Given a 2-3h budget on this hardware, you likely get **1-3 effective passes (epochs)** over the filtered set at best — don't expect many more. Re-run the pass-rate pre-filter once after the pilot run too, since the model's difficulty distribution shifts.
4. **Mixing in SFT data**: a small amount of SFT-style supervised replay or periodic SFT-loss regularization is a common practical guard against catastrophic forgetting during short/aggressive RL (this logic underlies why many R1-style recipes alternate SFT and RL stages, e.g. DeepSeek-R1's own multi-stage pipeline, and why Tulu 3 treats RLVR as one stage layered after SFT+DPO, [Tulu 3 paper](https://arxiv.org/abs/2411.15124)). For LoRA specifically, since you're not touching base weights, forgetting risk is lower, but mild KL (§1) plus occasional spot-check against your held-out pilot test set serves the same purpose more cheaply than literal SFT-data mixing within the GRPO loop (TRL's `GRPOTrainer` doesn't natively support interleaved SFT batches).

## 5. Running practice — monitoring, eval, failure modes

**Core metrics to watch** (all natively logged by TRL — [HF GRPOTrainer docs, Logged metrics](https://huggingface.co/docs/trl/main/en/grpo_trainer)):
- `reward` (mean) and `reward_std` — reward should trend up, slowly, from your ~0.96-equivalent baseline; watch for it plateauing immediately (dead gradient) or oscillating wildly (LR too high / clipping too loose).
- `frac_reward_zero_std` — your single most important diagnostic given the near-ceiling starting point; if this stays near 1.0 throughout, your curriculum filter (§4) isn't aggressive enough, or group size G is too small to surface variance.
- `kl` — only logged if `beta≠0`; if you set a small beta, watch for runaway KL (divergence from SFT reference) as an early-stop trigger.
- `entropy` — DAPO's central motivating failure mode is **entropy collapse** (completions in a group become near-identical) which stalls exploration ([DAPO §3.1, Figure 2](https://arxiv.org/html/2503.14476v2)); if entropy craters quickly, raise temperature or `epsilon_high`.
- `completions/mean_length`, `completions/clipped_ratio` — watch for length growth (the Dr. GRPO/DAPO length-bias failure mode) and for a rising clipped-completion fraction, meaning `max_completion_length` is too tight for your thinking+JSON output.
- `clip_ratio/region_mean`, `clip_ratio/high_mean`, `clip_ratio/low_mean` — fraction of (token or sequence) probabilities being clipped; sustained high clip ratio suggests the policy is trying to move faster than ε allows (consider Clip-Higher) or that LR is too high.

**Eval cadence / checkpoint selection.** With only ~100 steps available, evaluate on your held-out pilot test set every 10-20 steps (cheap relative to training rollouts, since eval can use greedy/low-temperature decoding and is typically much faster than multi-sample GRPO rollouts) and **checkpoint on pilot-set slot-F1 / record-F1, not training reward** — training reward on a filtered "hard cases" subset is not representative of your true target distribution and can look good while true generalization regresses (classic reward-hacking-via-overfit-to-curriculum risk). Keep at least 2-3 checkpoints and manually inspect decoded JSON outputs at each, specifically watching for the null-hacking and verbosity-growth failure modes flagged in §3.

**Signs of collapse / typical LoRA+small-model failure modes:**
- Sudden reward drop coincident with KL spike → LR too high or beta=0 allowed too much drift; roll back and restart with beta>0 or lower LR.
- Degenerate output ("thinking" loops repeating tokens, or empty JSON) → entropy collapse or clipped sampling; check `entropy` and `completions/clipped_ratio` first.
- Reward plateaus immediately at step 1 with `frac_reward_zero_std`≈1 → curriculum not filtered enough, or G too small — easiest fix is tightening the offline pre-filter (§4) rather than hyperparameters.
- Known LoRA-specific risk: with rank 32 and rsLoRA already saturated from 2-epoch SFT, the adapter has limited remaining capacity to shift behavior; if reward genuinely can't move even on filtered hard prompts, this may indicate the adapter (not the hyperparameters) is the bottleneck — consider whether a slightly higher-capacity adapter or merging+requantizing before RL would help. *Uncertain, not covered directly in surveyed sources — an inference based on general LoRA capacity/RL literature, not a specific citation.*

**Thinking-mode specifics for Qwen3.** Keep the `<think>...</think>` block during RL (don't strip it) — it's part of what the SFT adapter was trained to produce and stripping it mid-RL changes the action space the policy was shaped for. Qwen3's own technical reporting on its "thinking mode" and GSPO's use in "the latest Qwen3 models" ([GSPO abstract](https://arxiv.org/abs/2507.18071)) indicates the Qwen team itself uses GRPO/GSPO-style RL while preserving extended thinking; monitor `completions/mean_length` specifically to catch any runaway "thinking inflation" in the reasoning segment (a widely observed DAPO/Dr. GRPO failure mode), which is especially costly on your hardware since longer completions directly inflate already-slow HF-generate rollout time.

## 6. Small-GPU practicalities (RTX 3070 8GB, no vLLM)

- **Unsloth QLoRA + GRPO memory tips**: load with `fast_inference=False` for models unsupported by vLLM or when you want to avoid vLLM's extra memory reservation entirely — explicitly documented by Unsloth for exactly this scenario ("You can also run RL with Unsloth on models not supported by vLLM... simply set `fast_inference=False`" ([Unsloth Advanced RL docs](https://unsloth.ai/docs/get-started/reinforcement-learning-rl-guide/advanced-rl-documentation.md))). Unsloth states 15GB VRAM suffices up to ~17B models and as little as 5GB for ≤1.5B models with their memory optimizations ([Unsloth RL Guide](https://unsloth.ai/docs/get-started/reinforcement-learning-rl-guide)) — your 4B model on 8GB with QLoRA is within the documented envelope but near its tighter end, so watch memory headroom closely, especially with longer completions.
- **Gradient checkpointing**: TRL's `GRPOConfig` defaults `gradient_checkpointing=True` (overriding the generic `TrainingArguments` default of `False`) specifically for GRPO's memory profile ([TRL config source](https://raw.githubusercontent.com/huggingface/trl/main/trl/trainer/grpo_config.py), "Parameters whose default values are overridden" note). Keep this on; it's essential at 8GB.
- **Batch size / num_generations relationship**: TRL/Unsloth's formulas — `effective_batch_size = steps_per_generation * num_processes * per_device_train_batch_size`; `unique_prompts = effective_batch_size / num_generations` (must be **> 2**); `optimizer_steps_per_generation = steps_per_generation / gradient_accumulation_steps` ([Unsloth Advanced RL docs](https://unsloth.ai/docs/get-started/reinforcement-learning-rl-guide/advanced-rl-documentation.md), "Quick Formula Reference" + worked examples). On a single GPU, the practical path is: pick `num_generations=G` (8-12), set `per_device_train_batch_size` to a small number of unique prompts' worth of generations your 8GB can hold at once (likely 1-2 prompts' worth given 1.5k-3k token prompts + 600-token completions on a 4B model), and use `gradient_accumulation_steps`/`steps_per_generation` to reach a reasonable effective batch (e.g., effective batch 8-16 unique prompts) without requiring everything resident in VRAM simultaneously.
- **Throughput expectations without vLLM**: HF `generate()` is markedly slower than vLLM/continuous-batching, and TRL explicitly offers a middle-ground — **`use_transformers_continuous_batching=True`** — as "a drop-in upgrade with no server setup... well-suited for single-GPU training or memory-constrained environments," though for max throughput "use vLLM instead" ([HF GRPOTrainer docs, "Speed up training with transformers continuous batching"](https://huggingface.co/docs/trl/main/en/grpo_trainer)). **This is directly actionable for you**: since you're on HF generate with `fast_inference=False`, enabling `use_transformers_continuous_batching=True` with a tuned `max_memory_percent` (TRL defaults `0.5`, suggests `0.3-0.4` for larger generation batches to leave VRAM for backward pass) could meaningfully improve rollout throughput within your 2-3h budget without needing vLLM compatibility at all.
- Given slow rollouts, expect your realistic step budget to be the single biggest constraint on this run — prioritize curriculum filtering (§4) and a tight `max_completion_length` over trying many hyperparameter variants.

| `gradient_checkpointing` | `True` (default) | Essential at 8GB | [TRL config](https://raw.githubusercontent.com/huggingface/trl/main/trl/trainer/grpo_config.py) |
| `use_transformers_continuous_batching` | `True`, `max_memory_percent=0.35` | Faster/leaner generation without vLLM | [HF GRPOTrainer docs](https://huggingface.co/docs/trl/main/en/grpo_trainer) |
| `reward_weights` | weight JSON-validity low/asymmetric; balance recall (slot/record-F1) vs precision (hallucination/decoy) penalties | Avoid null-hacking and format-gaming | [Tulu 3](https://arxiv.org/abs/2411.15124) (general RLVR reward-hacking discussion) |

## (b) Step-by-step run protocol

1. **Pre-filter**: Score all ~500-600 prompts with current SFT adapter at train-time sampling settings (G=8, T=0.8-1.0); drop prompts with zero reward-std (both all-max and all-zero groups). Expect to retain a subset with genuine partial-success variance.
2. **Pilot run** (~20-30 min): Train ~20-30 steps on the filtered subset with the config above; verify `frac_reward_zero_std`, `entropy`, `clip_ratio/*`, and `completions/mean_length` behave sanely; spot-check decoded JSON for null-hacking/verbosity.
3. **Tune**: Adjust `scale_rewards`, `beta`, `epsilon_high` based on pilot diagnostics; re-run pre-filter if the model's difficulty distribution shifted noticeably.
4. **Full run** (remaining ~1.5-2h): Train to step budget, evaluating on held-out pilot test set every 10-20 steps; checkpoint on pilot slot-F1/record-F1.
5. **Eval & select**: Compare final checkpoints against the original SFT-only baseline on the full pilot test set across all reward components (not just aggregate), confirming no regression in recall (null-hacking check) or JSON-validity, and genuine improvement on the hard-case categories (long-range values, header propagation, distractors, multi-entity) the RL set targeted.
